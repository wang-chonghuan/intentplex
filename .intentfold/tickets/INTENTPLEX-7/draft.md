# INTENTPLEX-7 — 议定的做法

approach 是在对话里议定的（人类先问「图片如何处理，转 webp 存 easyapp blob，还是放 cloudflare cdn」，
我给出实测数据后建议两者都先不做，人类答「开，修吧」），所以不再 grill。

## 议定的结论

**blob 和 CDN 现在都是答非所问。** 先把体积问题解决掉，存储问题就自己消失了：

1. **删孤儿** —— 81/145 张无人引用，占 41.5MB。这是最大的一块，且零风险。
2. **按实际渲染宽度缩图** —— 原图 2048px，站点最宽容器 1080px。长边压到 1280 覆盖 retina。
3. **转 WebP** —— 同画质再省 25–35%。

实测三步合计 56MB → 4.1MB。到这个量级，「放哪」不再是个问题：留在仓库里，跟着镜像走，
不新增源站、不新增主机名、不触发 `arch.md` redline 4，也保住 `arch.md` 承诺的「一个进程、
内容是仓库里的文件」。

4. **真正该修的是缓存头。** 静态资源响应里没有 `cache-control` / `etag` / `last-modified`，
   而文件名就是内容哈希。补上 `immutable` 长缓存，收益大于任何存储方案的更换。

## 明确排除

- **easyapp blob** —— 多一个源站、一个主机名、一套访问配置、一步部署，换来的只是从一个几秒
  推完的镜像里挪走几 MB。
- **Cloudflare R2 / Images** —— 同上，且要花钱。若将来仍想要 CDN，最便宜的正解是把 apex 在
  Cloudflare 翻成橙云（域名本就在那儿，现在是灰云因为当初 Azure 证书走 HTTP 验证），
  零新存储、零代码改动。这是独立决定，不在本工单。
- **git 历史重写** —— 那 56MB 已经在 objects 里，转换不会让已有 clone 变小。要消除需
  `filter-repo`，独立决定。
